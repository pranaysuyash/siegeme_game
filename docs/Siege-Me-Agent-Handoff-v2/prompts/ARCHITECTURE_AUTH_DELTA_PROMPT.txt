ARCHITECTURE/AUTH UPDATE — APPLY THIS BEFORE CONTINUING

The active Siege Me architecture is now Cloudflare-first. Treat this as authoritative and superseding any Supabase or mandatory-login assumptions.

1. LIVE AUTHORITY
Use one named Cloudflare Durable Object (`SiegeWorld`, e.g. `global-throne-v1`) as the source of truth for the one global throne/world.

It owns:
- current reign/ruler
- Core Integrity
- persistent fortress state
- shields/braces
- attack queue
- active turn
- live entitlement balances
- Siege Charge / Royal Guard Charge
- world version/event sequence
- defeat/succession
- live WebSocket connections

Do NOT use D1, KV, Vercel functions, or browser state to arbitrate current ownership or victory.

2. REALTIME
Use Durable Object WebSockets, preferably Hibernation.

3. D1
Use D1 only for durable ledgers/archive/query data:
- Dodo webhook/payment/idempotency records
- public identity metadata
- entitlement ledger
- reign archive/history
- moderation/audit/recovery

D1 is NOT the live throne authority.

4. R2
Use R2 for normalized logos/avatars and other blobs.

5. KV
Optional cache/config only. Never authoritative.

6. PAYMENTS
Dodo webhook is payment authority.

Flow:
Dodo webhook
→ Cloudflare Worker verifies signature/idempotency
→ D1 records payment/entitlement ledger
→ Worker sends idempotent entitlement grant to SiegeWorld DO
→ DO stores live entitlement
→ player can use shots/defense

Checkout return/client state alone must NEVER mint an entitlement.

7. PLAYER IDENTITY
A stable player identity is required technically, but there is NO mandatory signup/login before play.

On first meaningful interaction:
- Worker silently issues internal `player_id`
- signed secure HttpOnly session cookie/token
- no UI

Spectators remain frictionless.

8. PROGRESSIVE AUTH / RECOVERY
Do not build a traditional auth wall.

Use:
anonymous spectator
→ silent player ID
→ paid player
→ recoverable identity only when valuable

After winning the throne, strongly prompt/require recovery setup so the ruler can control the throne cross-device and receive under-siege notifications.

Preferred first recovery method:
- email magic link through a transactional email provider

No passwords required initially.
No Supabase Auth / Clerk / Auth0 unless we explicitly revisit that decision.

9. PUBLIC IDENTITY != PLAYER IDENTITY
Keep separate:
- `player_id`: controller/payer
- `public_identity_id`: person/company/product/project/community shown on the throne

10. SAME-DEVICE VS CROSS-DEVICE
Signed session is enough for same-device play/queue/entitlements/ruler control.
Cross-device recovery requires attached recoverable identity.

11. DO NOT REINTRODUCE SUPABASE
Do not restore Supabase for realtime, database, storage or auth unless there is a concrete requirement Cloudflare cannot satisfy and you document the tradeoff first.

Read `implementation/ARCHITECTURE_AND_PLAYER_IDENTITY_CORRECTION.md` in the handoff kit before continuing.
